# Bad Case 复盘 #01：广州仓灰度期间误推全量订单

| 属性 | 内容 |
|------|------|
| **Case ID** | BC-20260708-001 |
| **发生时间** | 2026-07-08 14:32 ~ 16:18（约 1h 46min） |
| **影响范围** | 广州仓（WH-GZ-001）灰度期间多承接 **1,247 单**（预期 10% 约 420 单） |
| **严重等级** | P2（功能异常，无资损，履约正常） |
| **复盘人** | wzp |
| **复盘日期** | 2026-07-10 |

---

## 1. 事件概述

广州仓于 2026-07-01 进入「灰度运行（10% 流量）」状态。7 月 8 日下午运维同学修改 Nginx 配置做性能优化时，误将灰度流量开关 `route.trial.ratio` 从 `0.1` 改为 `1.0`，导致约 1 小时 46 分钟内所有华南订单均被路由至广州仓，而非预期的 10%。

---

## 2. 时间线

| 时间 | 事件 |
|------|------|
| 07-01 | 广州仓切灰度，配置 10% 流量 |
| 07-08 14:32 | 运维修改配置，`trial.ratio` 被设为 1.0 |
| 07-08 15:10 | 广州仓负载从 45% 升至 72%，WMS 作业延迟告警 |
| 07-08 15:28 | 运营主管收到企业微信「跨仓占比异常」通知（反向：广州仓占比突增） |
| 07-08 15:45 | wzp 排查配置，发现 ratio 异常 |
| 07-08 16:18 | 配置回滚至 0.1，负载恢复正常 |

---

## 3. 影响评估

| 维度 | 影响 |
|------|------|
| 订单量 | 多路由 827 单至广州仓（1,247 - 420） |
| 履约 | 全部正常发出，无丢单、无错发 |
| 成本 | 部分本应从武汉/长沙发的单改从广州发，成本基本持平或略优 |
| 负载 | 广州仓短时负载 72%，未触发 >80% 降级 |
| 用户 | 无客诉（实际履约更快） |

**结论：** 功能性配置错误，因「多路由到近仓」方向，未造成负面用户感知，但暴露了灰度机制的配置风险。

---

## 4. 根因分析（5 Why）

1. **为什么多推了订单？** → 灰度比例被设为 100%
2. **为什么比例变了？** → 运维改 Nginx 配置时误改同名环境变量
3. **为什么误改没被发现？** → 配置变更无 Code Review，无灰度比例变更告警
4. **为什么无告警？** → V1.0 健康监控未覆盖「灰度比例突变」场景
5. **为什么没做？** → 一期聚焦业务规则巡检，遗漏了 infra 层配置监控

**根因：** 灰度流量控制依赖单一配置项，缺乏变更审批、变更告警与配置漂移检测。

---

## 5. 改进措施

| 措施 | 负责人 | 状态 | 完成时间 |
|------|--------|------|----------|
| 灰度比例变更接入操作日志 + 企业微信通知 | 后端 | ✅ 已完成 | 07-12 |
| 健康监控新增「灰度比例突变」巡检项（1h 内变化 >20%） | wzp + 后端 | ✅ 已完成 | 07-15 |
| 配置变更纳入 GitOps，禁止生产环境直接改 | 运维 | ✅ 已完成 | 07-20 |
| 规则配置页展示当前灰度实际比例 vs 配置比例 | 前端 | 🔄 进行中 | 07-25 |

---

## 6. 经验沉淀

### 做对的
- 健康监控的「跨仓占比异常」反向触达，15 分钟内发现问题
- 回滚方案清晰（改配置即恢复），无需发版

### 待改进
- **灰度不是配个数字就完事**，要有配置漂移检测
- 产品要在 PRD 里明确「infra 层配置」的监控边界，不能只管业务规则

### 面试话术
> 「我们广州仓灰度时运维误把 10% 改成 100%，健康监控的跨仓占比告警反向发现了问题。复盘后加了配置漂移检测和 GitOps，产品侧也补了灰度比例的实时展示。」
