## 复盘方法论

每个 Bad Case 固定五段式：

```
用户问题 → AI 实际表现 → 根因分类 → 修复动作 → 策略/指标调整
```

**根因分类（本项目使用）：**

| 代码 | 含义 |
|------|------|
| K1 | 知识缺失（知识库没有相关内容） |
| K2 | 知识过期（文档过时未更新） |
| R1 | 检索错误（有相关文档但没召回到） |
| R2 | 检索片段切分不当（chunk 截断导致误解） |
| B1 | 边界判断错误（该转人工没转 / 该审核直接发了） |
| G1 | 生成幻觉（编造政策或承诺） |
| D1 | 数据源不一致（API 与页面数据不同步） |
| P1 | Prompt / 话术问题（表达不当、语气问题） |

## Bad Case #1：物流信息不一致导致用户点踩

### 基本信息

| 字段 | 内容 |
|------|------|
| 会话 ID | conv-2（李女士） |
| 用户问题 | 「我的快递到哪了？已经三天了还没更新物流信息，订单号 ORD20260703002」 |
| AI 回答 | 「快递已到达广州分拨中心，预计明天送达。因华南暴雨延迟 1-2 天。」 |
| 用户反馈 | 👎 信息不准确 · 继续追问：「物流页面一直没更新，我不相信这个结果」 |
| Case 类型 | Case A（本应高置信度）→ 用户不满意 → 待客服复核 |

### AI 实际表现

- 置信度：0.92（系统判定为高置信度，已自动回复）
- 引用来源：物流系统 API 查询
- 问题：用户端物流详情页仍显示「运输中 / 未更新」，与 AI 回答矛盾

### 根因分析

| 根因 | 说明 |
|------|------|
| **主因 D1** | 物流 API 与 C 端物流详情页数据不同步（API 已更新，页面缓存未刷新） |
| **次因 B1** | 高置信度阈值对「物流类」问题未区分数据源一致性校验 |

**不是 G1 幻觉：** AI 引用的 API 数据本身存在，但与用户看到的不一致。

### 修复动作

| 优先级 | 动作 | 负责方 |
|--------|------|--------|
| P0 | 物流类回答增加**双源校验**：API 结果 vs 用户端页面状态，不一致则降级为 Case B | 工程 |
| P0 | 回复文案增加缓冲：「以物流详情页实时更新为准，如有差异我帮您人工核实」 | PM + 运营 |
| P1 | 该会话标记 Bad Case，进入周复盘 | AI 运营 |
| P1 | 客服跟进话术入库 | 客服主管 |

### 策略调整

| 调整项 | 调整前 | 调整后 |
|--------|--------|--------|
| 物流类置信度阈值 | 0.85 | **0.90**（需双源一致才自动发） |
| 物流类 Case 默认 | A（自动发） | 双源不一致 → **B（审核）** |
| 监控指标 | 无 | 新增「物流类点踩率」专项监控 |

### PM 复盘结论

> **准确率 ≠ 用户满意度。** API 数据「正确」但用户页面「看不到」，在用户视角就是 AI 答错了。 要盯的不只是模型，还有**数据源一致性**。

## Bad Case #2：质量投诉场景 AI 险些过度承诺

### 基本信息

| 字段 | 内容 |
|------|------|
| 会话 ID | conv-1（张先生） |
| 用户问题 | 「我买的 T 恤洗了一次就严重缩水，根本穿不了，你们这质量也太差了！」 |
| AI 草稿 | 认定质量问题 + 支持退换 + 「建议换新或申请退款，具体金额以售后审核为准」 |
| 置信度 | 0.78（中置信度 → 正确进入待审核队列） |
| Case 类型 | Case B ✅（分流正确） |

### AI 实际表现

- **做对了：** 没有自动发送，进入客服审核队列
- **风险点：** AI 草稿中「属于质量问题」表述较强，若客服未审核直接发出，可能引发后续赔偿预期
- **用户情绪：** 激动（「质量也太差了」），AI 判断为「情绪：激动」✅

### 根因分析

| 根因 | 说明 |
|------|------|
| **R2** | 检索到退换货政策 + 商品详情「3-5% 轻微缩水」两条知识，AI 正确综合但语气偏「定性」 |
| **P1** | 草稿缺少「需实物确认」的缓冲表述 |
| **非 B1** | 分流逻辑正确，Case B 救了这一单 |

### 修复动作

| 优先级 | 动作 | 负责方 |
|--------|------|--------|
| P1 | Prompt 增加约束：质量投诉类**不得直接定性**，用「根据您描述的情况，初步判断可能涉及…」 | PM + 算法 |
| P1 | 推荐话术中增加「需您提供照片 / 需售后核实」步骤 | 客服主管 |
| P2 | 商品详情 chunk 增加元数据标签 `risk_level: medium` | 知识库运营 |
| P2 | 审核队列对该类问题**高亮「情绪风险」**标签 | 产品设计 |

### 策略调整

| 调整项 | 说明 |
|--------|------|
| 质量投诉类 | 永远 Case B，即使置信度 >0.85 也不自动发 |
| 审核 SLA | 中置信度队列要求 **3 分钟内** 客服响应 |
| 新增 red line | 草稿含「质量问题」「赔偿」关键词 → 强制人工审核 |

### PM 复盘结论

> 这个 Case 说明 **Case B 机制有效**。PM 的价值不是让 AI 更聪明，而是设计**「即使 AI 说多了，人也能拦住」**的流程。

## Bad Case #3：历史承诺争议 → 正确转人工但摘要不完整

### 基本信息

| 字段 | 内容 |
|------|------|
| 会话 ID | conv-3（王同学） |
| 用户问题 | 「你们上次答应我的处理为什么没兑现？我已经投诉过一次了，这次必须给我说法。」 |
| AI 回答 | 「涉及之前客服承诺和历史处理记录，已为您转接人工客服，并同步当前对话和相关订单信息。」 |
| 置信度 | 0.42（低置信度 → 正确转人工） |
| Case 类型 | Case C ✅（分流正确） |

### AI 实际表现

- **做对了：** 没有编造历史承诺内容，没有说「我们赔您 XX」
- **做对了：** 主动转人工，C 端展示等待状态
- **不足：** 转人工摘要中**缺少历史工单详情**（仅同步了当前对话 + 订单号，未拉取上次投诉处理记录）

### 根因分析

| 根因 | 说明 |
|------|------|
| **K1** | 历史承诺内容不在知识库，AI 无法检索（符合预期） |
| **工具链缺失** | CRM「历史工单详情」工具 V1 未接入，摘要只能同步当前 session |
| **非 G1** | AI 没有幻觉编造历史承诺 ✅ |

### 修复动作

| 优先级 | 动作 | 负责方 |
|--------|------|--------|
| P0 | 转人工摘要模板增加字段：历史工单 ID、上次处理结论、上次客服姓名 | PM |
| P1 | V1.1 接入 CRM 历史工单查询工具（只读） | 工程 |
| P1 | Case C 转人工时，B 端侧边栏**强制展示**「待核实：历史承诺内容」 | 产品设计 |
| P2 | 对该类会话标记 `complaint_escalation`，通知主管 | 运营 |

### 策略调整

| 调整项 | 说明 |
|--------|------|
| Case C 摘要必填项 | 当前诉求 + 订单 + 历史工单（有则填）+ 转人工原因 |
| 红线关键词 | 「上次答应」「投诉过」→ 置信度上限 cap 为 0.50，强制 C |
| V2 规划 | Agent 只读工具链：查历史工单 → 查处理记录 → 生成摘要 |

### PM 复盘结论

> **转人工不是失败，是产品设计的一部分。** Case C 的关键指标不是「AI 答对了没」，而是「客服接手后还要不要让用户重复描述」——摘要完整度才是体验核心。

## 周复盘机制（产品设计）

```
每周一 AI 运营例会
  ├── 拉取上周 Top 20 点踩 + Top 20 转人工
  ├── 按根因分类（K/R/B/G/D/P）
  ├── 分配修复 owner（知识库 / 工程 / Prompt / 流程）
  └── 更新 Golden Set + 回归测试
```

**PM 在复盘中的角色：** 判断是「知识问题」还是「策略问题」——前者补知识库，后者调阈值/改流程。
