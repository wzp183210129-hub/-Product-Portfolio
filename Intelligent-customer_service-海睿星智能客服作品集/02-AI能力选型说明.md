## 一、选型方法论

AI 产品经理选型的四步框架（本项目实际使用）：

```
① 判断业务问题类型（规则 / 预测 / 优化）
    ↓
② 匹配 AI 能力形态（知识系统 / Copilot / 决策引擎 / Agent）
    ↓
③ 划定能力边界（自动 / 确认 / 禁止）
    ↓
④ 用 Golden Set + Bad Case 验证可行性
```

**核心原则：** 先判断「企业在解决什么问题」，再决定「用什么 AI 形态」，而不是反过来。

## 二、业务问题分类 → 方案匹配

| 业务问题类型 | 典型用户问题 | 特征 | V1 优先方案 |
|--------------|--------------|------|-------------|
| **规则问题 Rule** | 「我的快递到哪了？」 | 条件明确、答案固定 | 规则引擎 + API 查询 + AI 意图提取 |
| **知识问题 Knowledge** | 「退货地址是什么？」「优惠券怎么用？」 | 答案在文档里，需检索引用 | **RAG 知识系统** ✅ |
| **优化问题 Optimization** | 「洗一次就缩水，能赔吗？」 | 多方案、需权衡成本/风险/满意度 | **Decision Engine + 人工确认** ✅ |
| **预测问题 Forecast** | 「这个用户会不会再次投诉？」 | 需历史数据建模 | 统计模型；LLM 只解释，不直接预测 |
| **多步任务 Agent** | 「帮我查退货单退款进度并催审」 | 需串联多个工具、维护状态 | **V2.0 再考虑** ⏳ |

## 三、AI 能力形态对比

| 能力形态 | 解决什么 | 优点 | 风险 / 局限 | V1 采用 |
|----------|----------|------|-------------|---------|
| **纯规则 FAQ** | 固定问答 | 稳定、可审计 | 覆盖窄、维护成本高 | 兜底方案 |
| **RAG 知识系统** | 基于文档生成有依据的回答 | 可引用来源、可更新知识库 | 依赖知识库质量；可能检索错 | **✅ 主方案** |
| **Copilot 副驾驶** | 帮客服分析、推荐话术 | 人机协作、降低新人门槛 | 需客服愿意采纳 | **✅ 主方案** |
| **Decision Engine** | 多方案推荐（退款/赔偿） | 结构化决策辅助 | 不能替代人工拍板 | **✅ 中置信度场景** |
| **Agent 自主智能体** | 多步任务自动执行 | 体验极致、省人力 | 资金/合规/不可控动作 | **❌ V2.0** |
| **端到端 LLM 直答** | 直接生成回复 | 开发快 | 幻觉、无来源、难审计 | **❌ 不采用** |

## 四、V1 为什么不做 Agent？

| 维度 | Agent 方案 | RAG + Copilot 方案 | V1 选择 |
|------|------------|---------------------|---------|
| **合规风险** | 可能自动发起退款、改订单 | 只读查询 + 人工确认写操作 | Copilot |
| **用户信任** | 黑盒执行，出错难追溯 | 每条回答带 doc_id/chunk_id 引用 | RAG |
| **上线速度** | 需工具链、状态机、权限体系 | 知识库 + 审核队列即可 MVP | RAG |
| **失败兜底** | Agent 卡住用户体验差 | 置信度低 → 转人工 | 分流机制 |
| **团队能力** | 需 MLOps + 工具编排 | 标准 RAG 链路，业界成熟 | RAG |

**结论：** V1 目标是跑通「AI 回答 → 用户反馈 → Bad Case 回流 → 知识库优化」闭环，而不是追求自动化率数字。

## 五、三层 AI 能力边界（V1 定稿）

| 层级 | 定义 | 具体内容 |
|------|------|----------|
| ✅ **自动执行** | AI 直接完成，无需人工 | 查物流、查订单、FAQ 政策说明、工单分类打标、标准话术 |
| ⚠️ **推荐 + 确认** | AI 出建议，人工拍板 | 退款/赔偿方案、投诉升级判断、敏感问题回复 |
| 🚫 **禁止触碰** | 任何情况不让 AI 做 | 操作资金、承诺赔偿金额、透露他人信息、自行发短信/邮件 |

**设计金句（面试可用）：**

> AI 负责「信息层」——查、找、整理、建议；人负责「决策层」——判断、承诺、担责。

## 六、置信度分流策略

| Case | 置信度区间 | 典型场景 | C 端表现 | B 端表现 |
|------|------------|----------|----------|----------|
| **A** | ≥ 0.85 | 物流查询、标准 FAQ | AI 直接回复 + 来源引用 | 记录「AI 已回复」 |
| **B** | 0.60 – 0.85 | 质量投诉、政策边界、用户情绪激动 | 「正在为您核实」→ 客服确认后发送 | 待审核队列 |
| **C** | < 0.60 | 历史承诺争议、强投诉、知识库无匹配 | 主动转人工 + 等待状态 | 人工队列 + 摘要同步 |

**为什么 C 端不展示置信度？**

- 用户看到「置信度 78%」会增加不信任感
- 产品用 **行为** 表达置信度：直接答 / 正在核实 / 转人工
- 具体分数只在 B 端供客服和运营决策

## 七、V2.0 演进路径（Agent 何时引入）

| 阶段 | 能力 | 前置条件 |
|------|------|----------|
| V1.0 | RAG + Copilot + Case 分流 | — |
| V1.1 | Bad Case 闭环、知识库运营后台 | V1 有效 AI 解决率 ≥50% |
| V1.5 | Agent **只读**工具链（查退货单→查退款流水→汇总） | 工具调用成功率 ≥95% |
| V2.0 | Agent **写操作**（建工单、催审，仍不自动退款） | 合规审计链路完善 |

**Agent 引入的判断标准：**

1. RAG 有效回答率已稳定在 70%+
2. Top 50 高频问题知识库覆盖率 100%
3. Bad Case 有固定周复盘机制
4. 写操作有完整 audit log 和人工兜底

## 八、与算法 / 工程的协作界面

| 我（PM）负责 | 算法 / 工程负责 |
|--------------|-----------------|
| 定义 Golden Set（50 条测试题 + 期望要点） | 实现 RAG 检索链路 |
| 定义置信度分流规则与 red line | 实现意图识别与置信度打分 |
| 定义 Bad Case 分类（知识缺失/检索错/边界错） | 实现日志埋点（session_id, citations 等） |
| 每周复盘 Top 10 点踩 / 转人工原因 | 优化 chunk 策略与 embedding |
| 验收：C 端不展示分数、B 端审核队列必达 | 性能：P95 ≤4s |
