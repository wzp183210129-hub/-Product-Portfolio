# 星途-RAG 知识库平台｜AI 能力选型说明

> 版本：V1.0｜作者：wzp  
> 目标：为企业知识治理、检索和问答选择可落地、可替换、可评测的 AI 能力组合。

## 1. 选型结论

星途-RAG 不把某个大模型或 RAG 平台当作产品本身，而采用“治理平台 + Provider Adapter + 可替换能力组件”的架构。

### MVP 推荐

- **RAG 编排引擎**：FastGPT；
- **文档解析**：引擎内置解析 + 独立 OCR/表格解析服务；
- **Embedding**：中文与中英混合表现稳定的通用向量模型；
- **检索**：关键词 BM25 + 向量的混合检索；
- **Rerank**：独立跨编码器重排模型；
- **生成模型**：企业批准的大语言模型，通过统一模型网关调用；
- **评测**：规则指标 + LLM Judge + 人工抽检；
- **安全**：身份权限、Chunk ACL、敏感信息检测和答案策略共同控制。

### 生产演进

保留 FastGPT 作为首个 Provider，同时建立标准适配接口，使 Dify、自研 RAG 服务或其他引擎可以替换。业务版本、审核、评测和发布状态始终保存在星途平台，不把关键治理数据锁定在外部引擎中。

## 2. 选型原则

### 2.1 业务效果优先

不以模型参数量、榜单名次或供应商品牌直接做决定。所有候选能力必须在公司的真实文档和真实问题上评测。

### 2.2 可解释

检索必须返回文档、版本、章节、Chunk、原文位置、召回分数和重排分数。不能只返回一个最终答案。

### 2.3 可替换

解析、Embedding、向量库、Rerank 和生成模型通过接口隔离。更换供应商不应影响平台中的业务版本和审计证据。

### 2.4 安全可控

浏览器不保存模型或 RAG 引擎密钥；企业服务端执行鉴权、权限过滤、限流、日志、脱敏和输出安全检查。

### 2.5 成本与性能平衡

Embedding 和索引是批处理成本，Rerank 和生成是在线成本。先通过检索过滤减少无效上下文，再调用生成模型。

### 2.6 以评测驱动迭代

任何模型、Prompt、切片和检索参数变更都要运行固定回归集，不凭少量 Demo 主观判断。

## 3. RAG 编排引擎

### 推荐：MVP 使用 FastGPT

选择理由：

- 覆盖文档处理、知识库、检索、工作流和 API 调用的基础能力；
- 能较快验证端到端链路，降低 MVP 工程投入；
- 支持将解析、检索和问答作为后台能力接入；
- 便于通过 API 与星途治理平台形成职责分工。

星途平台仍负责：

- 企业知识库和业务版本；
- 审核、处理验收和发布审批；
- 测试/生产环境映射；
- 角色、数据权限和审计；
- 批量评测、发布门槛和 Bad Case。

不直接把引擎管理后台交给普通运营人员，避免业务状态与底层资源状态脱节。

### 候选：Dify

适合需要更强应用编排、工作流和多模型快速试验的场景。若项目后续重点转向 AI 应用搭建，可作为第二个 Provider 接入。

### 候选：自研 RAG 服务

适合以下情况：

- 对解析、检索或权限有深度定制要求；
- 知识规模、并发或延迟达到现有引擎瓶颈；
- 需要完全私有化和自主可控；
- 团队具备检索、模型服务、可观测性和长期运维能力。

不建议在 MVP 首期完全自研，因为会把项目重心从知识治理转移到基础组件建设。

## 4. 文档解析与 OCR

### 能力要求

- 支持 PDF、DOCX、PPTX、XLSX、HTML、Markdown 和 CSV；
- 识别标题层级、列表、表格、页码、图片和脚注；
- 扫描件支持 OCR；
- 解析结果可定位至原文页码或段落；
- 输出统一结构化格式，例如 Markdown + 元数据；
- 对加密文件、空文件、乱码和超大文件给出明确错误。

### 选择策略

- 普通 Office 文档优先使用结构解析，不要全部转图片 OCR；
- 扫描 PDF 使用 OCR，并保留坐标信息；
- 表格密集文档使用具备表格结构恢复能力的解析器；
- 合同、制度和说明书按章节结构切片；
- FAQ 和表格优先转为结构化记录。

### 验收指标

- 正文完整率；
- 标题层级保留率；
- 表格单元格准确率；
- 页码定位成功率；
- 乱码和空白页比例；
- 条件、例外和列表是否被错误拆分。

## 5. Chunk 切分

### 推荐方案：结构优先的混合切片

1. 先按标题和段落识别文档结构；
2. FAQ 按单条问答切分；
3. 表格按完整业务语义保存；
4. 长章节再按 Token 上限递归切分；
5. 相邻片段保留适度重叠；
6. 每个 Chunk 附加文档标题、章节路径、版本和权限元数据。

### 不推荐

- 所有文档统一按固定字符数切片；
- 将表格标题和表格正文拆开；
- 将条件、结论、例外分到不同 Chunk；
- 只保存纯文本，不保存原文位置和业务元数据。

### 初始参数

- 正文 Chunk：约 400～800 Tokens；
- 重叠：约 10%～15%；
- FAQ：一问一答为主；
- 表格：按完整主题或记录组；
- 最终参数必须用真实评测集调优。

这些数字是初始实验值，不应作为所有文档的固定标准。

## 6. Embedding 模型

### 候选方向

- 云端通用向量服务：部署简单、效果稳定，适合 MVP；
- 开源中文/多语言向量模型：适合私有化和成本可控场景；
- 行业微调模型：只有通用模型在真实评测上明显不足时考虑。

### 评估维度

- 中文语义召回；
- 中英混合和专业缩写；
- 长文本支持；
- 向量维度与存储成本；
- 单批吞吐和 P95 延迟；
- 云端数据合规；
- 私有化算力需求；
- 模型升级后的向量兼容与重建成本。

### 推荐决策

MVP 可使用 `text-embedding-v3` 级别的企业批准向量服务作为基线，同时保留一个可私有化的中文向量模型作为对照组。使用公司真实问题测试 Top K 命中率，效果差异不显著时优先选择成本和运维更优方案。

## 7. 向量数据库

### 能力要求

- 支持向量和标量过滤；
- 支持租户、知识库、版本、有效期和 ACL 元数据；
- 支持索引增量更新、删除和版本切换；
- 支持数据备份、监控和容量扩展；
- 检索延迟满足在线问答要求；
- 具备稳定客户端和运维工具。

### 选择建议

- MVP 数据量较小时，可以沿用 RAG 引擎内置向量存储；
- 已有 PostgreSQL 技术栈且规模适中，可评估 pgvector；
- 规模较大、检索负载高或需要专门能力时，评估 Milvus 等向量数据库；
- 云环境优先评估现有云厂商托管能力，减少新增运维系统。

数据库选型不只看向量 QPS。星途场景中，稳定的元数据过滤、版本删除和权限控制更重要。

## 8. 检索策略

### 推荐：混合检索

同时执行：

- 向量检索：覆盖语义相似和口语表达；
- BM25 / 关键词检索：覆盖产品名、编号、条款和专有名词；
- 元数据过滤：控制版本、有效期、渠道、组织和用户权限；
- Rerank：对合并后的候选重新排序。

### 查询增强

按需启用：

- 缩写与同义词扩展；
- 多轮对话中的问题改写；
- 复杂问题拆分；
- 拼写纠正；
- 时间、渠道和产品过滤条件提取。

查询增强不能改变用户原始业务意图，原问题与改写结果都要记录。

### 无知识策略

当没有高置信、有效且有权限的证据时：

1. 不输出确定性业务结论；
2. 说明当前知识中没有可靠依据；
3. 对模糊问题提出澄清；
4. 提供人工渠道或后续动作。

## 9. Rerank 模型

### 为什么需要

Embedding 适合快速召回，但对细粒度条件、数字、否定表达和相似政策区分可能不足。Rerank 使用问题与候选片段联合计算，可提升正确片段的最终排序。

### 推荐策略

- 初步召回 20～50 个候选；
- 使用 `gte-rerank-v2` 级别能力作为基线；
- 重排后向生成模型提供约 3～8 个高质量片段；
- 对低分候选设置拒答或澄清阈值；
- 高风险场景使用独立阈值，不与普通 FAQ 共用。

### 评估指标

- Top 1 / Top 3 / Top 5 命中率；
- MRR 或 NDCG；
- P95 延迟；
- 单次成本；
- 否定条件、有效期和相似条款区分能力。

## 10. 生成模型

### 能力要求

- 中文指令遵循和信息抽取稳定；
- 能严格依据上下文回答；
- 支持结构化输出和引用编号；
- 对“没有依据”能正确拒答；
- 上下文窗口满足多片段输入；
- 延迟、成本和并发满足应用要求；
- 支持企业数据合规与日志控制。

### 模型分层

- **轻量模型**：问题分类、查询改写、标签提取、简单摘要；
- **主回答模型**：知识问答、多轮理解和结构化回答；
- **高能力模型**：复杂分析、高风险复核或离线评测；
- **私有化模型**：强数据隔离或离线环境。

不建议所有任务都调用最强模型。先按任务复杂度路由，可以降低成本和延迟。

### Prompt 原则

- 明确角色和业务边界；
- 只允许依据已授权上下文回答；
- 引用必须与具体结论对应；
- 冲突知识按有效版本处理；
- 证据不足时拒答或澄清；
- 不输出系统提示、密钥、内部权限信息和敏感实体；
- Prompt 版本纳入评测和发布管理。

## 11. AI 评测能力

### 规则指标

- 预期文档和 Chunk 是否命中；
- 引用是否存在、版本是否有效；
- 必填字段、数字和关键词是否正确；
- P0 禁止项是否出现；
- 延迟、Token 和成本是否超限。

### LLM Judge

用于评估：

- 答案正确性；
- 完整性；
- 忠实度；
- 引用支持度；
- 可读性。

LLM Judge 不能作为唯一结论。其模型、Prompt 和评分标准必须版本化，并通过人工样本校准。

### 人工评测

以下内容必须有人复核：

- 价格、合同、退款、数据安全等 P0/P1 问题；
- 模型评分与规则冲突的案例；
- 发布前随机抽样；
- 新业务或新文档类型；
- 线上真实 Bad Case。

## 12. 安全能力

### 输入侧

- 文件类型、病毒和恶意内容检测；
- 个人信息和敏感数据识别；
- Prompt Injection 检测；
- 数据源密级和 AI 使用许可校验。

### 检索侧

- 租户隔离；
- 知识库、文档和 Chunk 级 ACL；
- 有效版本、有效期和渠道过滤；
- 缓存键包含权限上下文。

### 输出侧

- 敏感实体检测与脱敏；
- 高风险结论规则校验；
- 引用有效性检查；
- 无依据答案阻断；
- 全链路 traceId 与审计。

安全不能只依赖 Prompt，必须由确定性的系统控制兜底。

## 13. Provider Adapter 设计

星途平台定义统一能力接口：

- `submitDocument`：提交文档或结构化内容；
- `getJobStatus`：查询处理状态；
- `getProcessingResult`：获取解析与 Chunk；
- `retrieve`：执行知识检索；
- `generate`：生成带引用答案；
- `publish`：切换生产资源；
- `disableVersion`：停用指定版本；
- `healthCheck`：连接与权限检查。

适配器将不同引擎的字段、错误码和异步方式转换为统一模型。平台保存外部任务 ID、资源 ID、参数快照和原始响应摘要。

## 14. 评测方案

### 离线评测集

- 真实高频问题；
- 标准答案和预期来源；
- 口语、缩写、错别字和多轮问法；
- 相似条款和历史版本干扰；
- 无答案问题；
- 越权和提示词注入；
- P0 高风险问题。

### 对比方法

一次只改变一个主要变量，例如：

- Embedding A vs B；
- 固定切片 vs 结构切片；
- 向量检索 vs 混合检索；
- 有无 Rerank；
- 生成模型 A vs B。

记录 Top K 命中、答案通过率、P0 失败、P95 延迟和单次成本，避免多项同时变化导致无法判断收益来源。

### 上线门槛

- P0 安全失败数为 0；
- Top K 召回和答案通过率达到业务阈值；
- 阻断问题全部关闭；
- 关键问题人工复核通过；
- 延迟和成本满足预算；
- 支持稳定回滚。

## 15. 成本控制

- 文档内容哈希不变时不重复解析和向量化；
- 新版本只增量处理变化内容；
- 查询改写使用轻量模型；
- 先检索和重排，再向生成模型提供精简上下文；
- 相同公开问题可在权限一致的前提下缓存；
- 离线批量评测设置预算和并发上限；
- 监控每个知识库、应用和模型的 Token 消耗。

## 16. 最终建议

首期以 FastGPT 快速跑通业务闭环，但产品设计从第一天就保持引擎中立。优先把资源投入到知识版本、权限、处理验收、真实评测集和 Bad Case 闭环，而不是过早微调大模型或完全自研向量基础设施。

选型是否成功，最终不看接入了多少 AI 名词，而看以下结果：

1. 正确知识能否稳定进入 Top K；
2. 模型能否只依据有效且有权限的证据回答；
3. 高风险错误能否在发布前被发现；
4. 线上问题能否快速定位到知识、检索或生成环节；
5. 模型或引擎更换时，业务治理能力是否仍然完整。
